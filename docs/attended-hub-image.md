# Actual hub-image metadata from the logging-only test

The saved 31 October image-source ETL now yields **259 consistent kernel-image rundown pairs**, including USBHUB3. The hub's size, PE timestamp and checksum match the pinned Microsoft disk image. This is actual image-window metadata evidence; the earlier USB control trace and failed second-open trace remain outside that qualification.

The [compact evidence](evidence/attended-hub-image-20261031.json) is generated by the [offline exporter](../scripts/export-attended-hub-image.py). It verifies the original failed source-run/cleanup outcome, source ETL and decoded XML hashes, the installed WMI schema snapshot and the original-image metadata comparison. Raw module addresses and other process-module paths remain in local analysis rather than the compact report.

The source contains 50,340 events, with zero reported event/buffer loss. The hub pair falls within the image source's approximately 1.77-second header window, 12:10:14–12:10:16 UTC. The configured five-second duration was interrupted by supervisor cleanup after the GUID-query rejection, so this does not establish autonomous timer expiry.

The initial strict checker understood only version 2. A read-only query of the installed Microsoft `root/wmi` classes now establishes `Image` event version 3 and the `Image_Load` payload's fourteen ordered fields, including two UInt8 signature properties and a UInt16 reserved property. Pointer-qualified fields remain pointer-sized even though their CIM base type is UInt32. The [schema-query script](../scripts/inspect-kernel-image-schema.ps1) creates a new metadata report without trace, device or privilege changes. The checker accepts exactly versions 2 and 3; version 3 requires that field set and numeric widths. Unknown versions, missing/extra properties and inconsistent pairs reject.

Microsoft's pinned [PerfView parser](https://github.com/microsoft/perfview/blob/9f071a5cb2e70cdfee13abc510344ab1e8840c90/src/TraceEvent/Parsers/KernelTraceEventParser.cs) corroborates the common image identity fields for versions at least 2 and permits extended records for later versions. The installed schema and actual named-property decode supply the specific version-3 evidence here. Signature level/type are preserved as event values; they are not independent signature verification or a cryptographic loaded-memory identity.

The ETL header also reports the prepared private session name and `LogFileMode=0x02000000`, confirming the system-logger bit in the produced file. It reports **MaxFileSize=0**: the requested 64 MiB segment setting was not an effective ETW hard file limit. That limit must not be described as enforced. The source stayed within the offline inspector's size bound and cleanup stopped/deleted its collector, then independently observed absence; the original run still fails its GUID check and is unchanged.

Fourteen standalone tests pass, including version-3 schema/width failures, process-versus-kernel separation and mixed-version pair rejection. The original Microsoft version-2 sample still decodes 179,474 events and 141 kernel pairs, with no USBHUB3 match. Compact report regeneration is byte-identical. No new source/session or USB operation ran during this analysis.

This closes the missing timestamp/checksum metadata for this image-source window. It does not retroactively identify the loaded image during the earlier USB trace, attest a PDB GUID from memory, repair successive acquisition or qualify USB readiness. The next investigation can use the saved live USB-state timeline with its version limits retained; an image source spanning a future USB interval still needs corrected identity/limit handling and its own validation.
