# USB arrival registration during Serato startup

## Live result after the one-time install

With the portable r2 package installed, both ordinary desktop-shortcut launches stayed offline. Serato's own logs recorded the rebuilt ASIO name during enumeration, a USB connection for the genuine SL3, passing firmware checks and `Device Added: Rane SL3`. Neither process produced an application-bound ASIO activation receipt. [Install trial](return-to-testing.md#one-time-install-trial)

A 52-second Windows debugger launch used the same executable, working directory and empty argument list as the shortcut. Hardware breakpoints observed the genuine SL3 message being constructed, policy return 0 and a listener count of **zero** for the same message at dispatch. The manager initializer did not run before that arrival, and the handler did not receive it. This establishes that the message was accepted and reached listener lookup, where there was nobody registered to consume it. It does not establish why the manager's normal startup trigger was absent. The earlier 16-second attempt detached before the application's device discovery and is inconclusive.

The 2.5.5 executable has a direct USB manager initialization call in its startup bootstrap. The corresponding checked call in 5.0 is in the Engine's handler for message `0x5d4`. The live result identifies the missing listener on this launch. [Historical and current call sites](evidence/serato-historical-usb-startup-20261107.json)

## Message registration and dispatch

Serato 5.0.0.1278 queues ordinary USB arrivals and resolves listeners when it processes each queued message. The USB audio manager can receive an arrival published before its subscription if the arrival was queued and the listener is registered when the drain takes its listener snapshot. The ordinary registration adds the listener without the separate lookup that marks existing startup-state records. [Original-byte evidence](evidence/serato500-usb-subscription-20261107.json).

The USB audio manager and the DeviceManager USB-only publisher use the same checked `MessageSystem` global. The arrival publisher constructs message `0x2d4` on route 7 and publishes through slot `+0x58`. The manager registers for that message on route 7 through slot `+0x10`. The checked registration path searches a vector for the listener and appends a 16-byte record when needed, including when the vector grows.

For `0x692`, the manager instead uses slot `+0x20`. That path registers in a separate keyed collection, then calls a helper that matches existing records by message, address, route and subtype. The helper marks the matching records at offset `+0x30`. The ordinary arrival registration has no corresponding call in the checked path. The static analysis leaves pending deliveries, new publications and other replay paths open.

The publish path checks the message and calls a policy callback before the enqueue at `141545ae0`. It can enqueue the original, replace it or return without queuing it. The enqueue stores the message and a flag in the queue at `MessageSystem+0x158`. The drain at `141546370` swaps the queue into a local batch, then looks up and copies the listener vector for each message. Both registration and dispatch index the same collection at `+0x28` using message, address and route. The USB arrival uses `(0x2d4, 0, 7)`. The drain calls listener slot `+0x08`; for the USB audio manager that slot forwards to `+0x18`, the existing handler at `1407108e0`.

The Engine's `0x5d4` branch calls three helpers in order. First it publishes two MIDI-side notifications, then can reconsider entries in the existing MIDI collection through `140525710` when either MIDI manager readiness byte is set. Next it obtains the USB audio manager, creating it if needed. The last helper checks for a non-null result from authorization slot `+0x98` and calls the USB state helper with the fixed tuple `13e5:13e5:13e5`. That call takes no USB identity from the message and supplies no SL3 descriptor. This leaves the actual arrival's queue and listener lookup as the points to observe if the normal launch remains offline. The checked Engine branch leaves other publication and replay paths open. [Instruction evidence](evidence/serato500-usb-subscription-20261107.json) · [Authorization receiver](serato-authorization-service.md) · [MIDI selection callback](serato-handshake-consumers.md)

The neighboring Engine message `0x2cb` takes a different path. It requires a true result from the Engine guard at `141373c10`. It can handle a diagnostic text payload, then publishes `0x2ca` with a null pointer on route 7. That message type returns false to the Engine's Boolean query, so a later delivery can take the existing disconnect path if the Engine was connected. Of 99 checked direct calls to the pointer constructor and forwarding helpers, two pass literal `0x2cb`. The Engine producer supplies its audio-connect error text, and the LicenseController updater supplies a null payload on its checked branch. The earlier fallback probe did not record either `0x2cb` origin. If a live trace sees selection followed by immediate loss, these two origins can distinguish a failed connect from a separate disconnect request.
