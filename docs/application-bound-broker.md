# Keep the SL3 broker alive for one application

The Windows broker now accepts an explicit `--application-process PID:CREATION_FILETIME` on its existing `--run` command. With this option, one controller can hold the SL3 while the same application releases and recreates ASIO objects. The controller begins its existing retirement sequence when that application exits. Its existing lifetime cap and explicit stop path still apply.

The controller opens and retains the application process with query and synchronization access. It checks the creation time and requires the same ordinary-user token context as the existing pipe admission. Before granting a client lease, the pipe also requires the client PID to match the still-live application process. The existing pipe identity challenge remains in place. The controller holds the process handle through retirement, so it waits on that object rather than polling for a process name or a reusable PID. It requires the application to be live at the acquisition and publication boundaries.

The intent records whether an application was bound. The result records whether its process handle signaled. A normal application exit after detach can end in a successful broker retirement. An interrupted stream retains its ownership failure alongside the independently observed worker exit and device release. The diagnostic lifetime remains at most ten minutes in unmeasured mode.

The Release build passed all 73 checks. The controller suite refused stale and malformed identities before creating a session. It then refused another client from the same Windows account and ran four simulated streams across three ASIO objects in the bound process. The worker audit recorded one acquisition and one release. Terminating a bound fixture after its callback barrier preserved the ownership failure and independently verified simulated I/O retirement, device release and an empty worker job. Separate runs at 44.1 kHz and 128 frames confirmed retirement on application exit and on lifetime expiry while the application was still alive. [Build and result evidence](evidence/application-bound-broker-20261107.json).

This is a broker capability. The installed ASIO activation path still owns its controller per ASIO session. Connecting that path to an application-bound controller requires starting or finding one verified controller for the process and allowing it to outlive a DLL unload. This checkpoint used simulated workers. The [attended Serato normal-start trial](retained-normal-start-trial.md) still uses the previously verified package and a broker started before Serato. That test determines whether Serato selects the driver on its normal entry path.
