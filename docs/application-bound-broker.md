# Keep the SL3 broker alive for one application

The Windows broker now accepts an explicit `--application-process PID:CREATION_FILETIME` on its existing `--run` command. With this option, one controller can hold the SL3 while the same application releases and recreates ASIO objects. The controller begins its existing retirement sequence when that application exits. Its existing lifetime cap and explicit stop path still apply.

The controller opens and retains the application process with query and synchronization access. It checks the creation time and requires the same ordinary-user token context as the existing pipe admission. Before granting a client lease, the pipe also requires the client PID to match the still-live application process. The existing pipe identity challenge remains in place. The controller holds the process handle through retirement, so it waits on that object rather than polling for a process name or a reusable PID. It requires the application to be live at the acquisition and publication boundaries.

The intent records whether an application was bound. The result records whether its process handle signaled. A normal application exit after detach can end in a successful broker retirement. An interrupted stream retains its ownership failure alongside the independently observed worker exit and device release. The diagnostic lifetime remains at most ten minutes in unmeasured mode.

The Release build passed all 73 checks. The controller suite refused stale and malformed identities before creating a session. It then refused another client from the same Windows account and ran four simulated streams across three ASIO objects in the bound process. The worker audit recorded one acquisition and one release. Terminating a bound fixture after its callback barrier preserved the ownership failure and independently verified simulated I/O retirement, device release and an empty worker job. Separate runs at 44.1 kHz and 128 frames confirmed retirement on application exit and on lifetime expiry while the application was still alive. [Build and result evidence](evidence/application-bound-broker-20261107.json).

## Automatic ASIO activation

The follow-up adds an opt-in `SL3-ASIO-ACTIVATION-2` header with the same ordered fields as version 1. A version 2 ASIO object starts or finds the controller during `IASIO::init`. Object creation remains passive. Version 1 continues to retire its controller when the ASIO session closes.

The driver reserves one create-new claim under the current user's private activation root, keyed by the process ID and Windows creation time. The startup thread writes a receipt containing the reviewed configuration identity and the hash of the controller's published ASIO configuration. Reopens verify that receipt and use the existing broker process and image checks. An incomplete receipt, changed configuration or expired controller cannot trigger another acquisition in that process.

A reopen now reads the receipt before opening the published configuration. If a prior startup left an incomplete receipt, the new ASIO object reports that controller cleanup is unverified and leaves the claim in place. The first object still reports the cleanup it actually observed. If receipt publication fails after controller startup, the first object runs bounded cleanup and keeps its result. The receipt uses the same format and commits on a complete synchronous write under the exclusive claim handle. Its scope is the lifetime of the current host process.

The Release regression starts a simulated controller that misses its readiness deadline. The first object records exact child termination and an empty job. A fresh ASIO object reports unverified cleanup without creating another controller, altering the claim or reporting device release. The updated application-bound package and setup window are prepared for attended testing. [Build, regression and package evidence](evidence/application-claim-failure-20261107.json)

The application controller has its own job and waits for the exact host process. The driver can release the controller job handle after successful startup. The controller's nested worker retains its existing containment and retirement path. This lets ASIO unload without releasing the USB connection before the next open.

It unloaded the ASIO DLL between opens, refused a conflicting lifetime configuration, then reopened the original configuration through the same live controller. A retained Windows handle verified that the controller stayed alive after the final DLL unload and exited after the host. The controller separately reported simulated I/O retirement and worker exit. ### Controller creation during application exit

The application-bound controller now starts running in its private Windows job at creation. Previously the driver created it suspended, assigned the job and then resumed it. If the application exited between those steps, the suspended controller could not run the code that observes the application's exit. The new path uses the Windows 10 or later job-list process creation attribute. The controller can still outlive the ASIO DLL and retire its own worker after the application exits. Its worker jobs continue to use kill on job close. [Windows job-list attribute](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute)

The simulated ASIO lifecycle also passed two streams across DLL unload and reopen, with controller retirement after the host exited. These tests cover the new launch and existing lifetime behavior. They did not force an exit inside the former suspended interval or acquire a physical SL3.

### Cancellation before device acquisition

The controller supplies its stop event and the exact application process handle to the retained owner. The owner checks both before launching the worker and again after the worker's greeting, immediately before sending `acquire`. If either is signaled it records `acquisition_cancelled`, closes the worker if it was launched and leaves `acquireAttempted` false. A canceled owner cannot retry. If the acquire request has already been sent, the existing bounded reply and retirement path still owns the result.

All 73 x64 Release checks passed. The cancellation fixtures verified that a pre-signaled stop prevents worker launch, and that a signal raised by a separate simulated worker during greeting prevents acquisition and lets that worker exit normally with an empty job. ### Stop during automatic startup

The controller publishes a separate `startup-stop.txt` after creating its private stop event and before opening the worker. The record identifies the live controller, its endpoint and the reviewed worker. If automatic ASIO startup misses its deadline, the driver can use this record during its existing cleanup window. It verifies the controller image and creation time and compares the record's live process with the exact child it launched before it signals the event. The controller still publishes the ASIO configuration and readiness only after acquisition succeeds.

A controller that has already sent a USB request may have to wait for the existing worker deadline and retirement checks. If it cannot stop within the grace period, ASIO still contains the exact child job. Startup remains failed in either case. A stop request or process exit alone gives no proof of USB release or readiness to reopen.
