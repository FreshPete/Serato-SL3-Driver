# Active session pointer under packaged Windows callers

The longer Phase test exposed a cleanup-only failure: a live session pointer's `Path.resolve()` returned Codex's packaged-app cache location while the pointer's logical parent resolved to native Local AppData. The bundle verifier interpreted that difference as an escaped destination and refused the ordinary broker-stop dispatch. The same verifier passed before publication and after verified pointer withdrawal.

The destination check now treats the pointer as a logical filename under a resolved, contained parent directory. It returns the original hash-bound path spelling. Parent traversal, relative destinations and parent junctions resolving outside the allowed root are refused. An existing pointer leaf must be a regular file without a reparse attribute; directories and symbolic/reparse leaves are refused. Binary/package destinations keep the existing full-path containment check. Actual pointer withdrawal still checks its ownership record, exact contents/hash and controller process identity; destination validation alone does not authorize deletion or native rollback.

Five focused tests pass. They cover absent/existing regular pointers, a redirected regular leaf, retained locator spelling, outside/relative/traversal paths, an escaped parent and directory/symlink/reparse leaves. A separate actual Windows fixture in the existing SL3 user-data directory reproduced the observed redirection: the old check refused it, the new pointer check accepted it, and its contents and original path spelling were preserved. Only that uniquely created fixture file was removed. All 26 deployment checks and 22 session checks pass. No device was opened for these checks. [Evidence and source hashes](evidence/pointer-redirection-fix-20261106.json)

The native DLL/worker binaries and their lifetime limits are unchanged. Existing source-bound capsules are intentionally stale after this script change and must not be reused; a fresh capsule, generated launcher, packaged installer resource and session plan are required.

The subsequent live retry validated this cleanup fix. While Serato was running, the actual published pointer resolved into the packaged-app cache, the old check refused it, and the corrected complete capsule verification passed without withdrawing it. The owner confirmed both tracks playing under Phase and later reported eight-bar loops on both decks. A five-second sample contained nonzero packed-24 audio on both logical deck pairs with no clipped samples. Serato later reached its nine-minute viewing limit and was force-closed; the broker preserved `client_control_abandoned`, so clean shutdown after playback is still unverified. Crucially, ordinary broker retirement and elevated rollback then completed automatically: original resources were restored and temporary registration, native files, permit, pointer and exact launcher cache were absent. No separate recovery prompt was needed. [Live retry and independent cleanup evidence](evidence/pointer-cleanup-live-retest-20261106.json)

The owner's later confirmation states both decks worked responsively and Serato closed normally. That report is retained alongside the process trace, which records observer-forced termination at the limit. The discrepancy is unresolved; successful Phase tracking and cleanup are recorded independently, without changing the trace or promoting the run to a verified normal exit.
