# Bounded continuous-worker/SDK callback probe

`sl3_host_probe` exercises the original production `HostSession`, isolated native worker, SDK buffer planes and callbacks without registering an ASIO COM device or creating a latency profile. Its default and `--plan` modes perform no device access. Explicit execution uses a hash-pinned worker and reviewed helper, twelve planes (six input/six output), 128-frame banks and 64 USB intervals per block. Its callback writes only zeros to output planes and checks logical frame-position increments. The requested streaming window is one second, with a 30-second private-process watchdog and the existing independent worker/audio retirement rules.

The separate executable `sl3_host_probe_simulated` is compiled with an explicit simulated identity. Production probe execution cannot accept a truthful simulated worker as native; that rejection is tested. Software tests exercise plan/argument gates, a real private process/SDK callback lifecycle with simulated transport, normal retirement/counters and wrong-kind rejection. Release and Debug each pass 31 native tests; SDK-free passes 21 and Python passes 42. These are distinct from hardware outcomes.

`HostReport` now retains its last decoded worker control snapshot, including transfer counters and pending/retained masks. It is not a continuously refreshed stream view and introduces no extra control request. This makes startup/stop outcomes inspectable without treating callback counts alone as proof of completed hardware output.

The wrapper `scripts/test-host-probe-traced.ps1` defaults to plan mode. Explicit `-Run` requires elevation, enabled Secure Boot, a running reviewed driver, current source/executable identities and same-worker validated capture/silent-duplex records. It captures the complete probe operation, decodes/checks trace loss and compares selected before/after state. No installer, firmware, rate setter, COM registration or audible signal is introduced.

A release/re-enumeration readiness gap is therefore a plausible explanation for the immediate-reopen failure. It is not yet proven to be the only cause.

## Enumeration readiness change

The native continuous-worker inspection and stream-target selection now allow up to two seconds for a unique SL3 to reappear. Only a successful enumeration containing zero matching devices is polled again, with at most 25 ms between polls. Each device list is released before waiting. Multiple matches, enumeration errors, malformed lists and descriptor mismatches still fail immediately; no redirect, control request or audio startup is retried. A device appearing at or after the deadline is rejected. Other finite diagnostics retain immediate selection.

The platform-independent readiness policy tests transient absence, deadline expiry, late appearance, ambiguity, monotonic-clock rollback, immutable terminal results and the original zero-wait policy. ## Callback delivery timing

The probe now retains the first 2,048 callback timing observations in fixed storage: logical bank frame, backend publication observation in nanoseconds, and callback-entry QPC ticks. The QPC frequency is recorded once before startup. The audio callback performs no allocation or file output. Records are published once with release/acquire ordering and never overwritten; progress snapshots can read the published prefix while callbacks continue. Excess observations increment an explicit dropped-record counter without changing audio behaviour.

`scripts/analyse-callback-timing.py PROBE_JSON` checks frame positions, clock monotonicity, integer bounds and coverage, then reports callback/publication spacing distributions and the software frame delivery rate over the recorded window. It reads saved metadata only. Multiple banks can share one publication observation, and the callback counter has no assumed common epoch with that observation. Only differences within each clock are compared.

The deliberately unpaced simulated worker fills this bounded store and reports dropped observations. The analyser exposes its much-faster-than-real-time delivery rather than treating the reported 48 kHz metadata or logical frame progression as clock proof. Synthetic tests also cover nominal delivery, a callback stall, batched timestamps, regressed clocks, frame gaps, inconsistent/truncated coverage and invalid counters.

This instrumentation establishes neither ADC/DAC timing, analogue round-trip latency nor gap-free USB delivery. It emits no approved timing profile. The probe uses **64 intervals per transfer**; the production ASIO facade uses **8**, so neither a later successful probe nor its timing statistics can be extrapolated into the production profile. Exact-mode continuous tests and a controlled physical loopback remain required. The native USB worker is unchanged by this instrumentation and retains SHA-256 `0051d6f004c49a6f3776edc70404d80f76bcea702241a014fe9e460cbad93ce1`.

The [software checkpoint](evidence/callback-timing-build.json) binds the tested source, binaries and logs. Release/Debug pass 32/32, SDK-free remains 22/22 and Python passes 48/48. No new administrator launch or physical test was attempted for these timing changes.

### Transport source narrows the next diagnostic

The exact reviewed UsbDk source commit exposes synchronous helper calls for enumeration, configuration reads and `AddRedirect`. The driver-side add path resets/re-enumerates the device and waits for redirector attachment; removal also waits for detachment. Both attachment and detachment waits allow **120 seconds**, and handle creation has a separate polling window. Consequently, a two-second enumeration policy and an eight-second worker watchdog cannot guarantee that a synchronous kernel operation has finished within those bounds. A termination request is not retirement proof. These are documented redirection internals, not new reset exports invoked by our program. [Helper operations](https://github.com/daynix/UsbDk/blob/84752c30037956149d53b498005b5368616f9257/UsbDkHelper/DriverAccess.cpp), [attachment wait](https://github.com/daynix/UsbDk/blob/84752c30037956149d53b498005b5368616f9257/UsbDk/ControlDevice.h#L195), [driver add/remove paths](https://github.com/daynix/UsbDk/blob/84752c30037956149d53b498005b5368616f9257/UsbDk/ControlDevice.cpp#L726).

The long-lived worker is consistent with such a wait but does not identify the blocked call. The next diagnostic must persist entry/return markers around helper load, enumeration, configuration read, redirect start, getter and redirect close, including an inspection-only rapid-reopen case. It should distinguish close/reopen readiness from the request engine before any further audio attempt. A persistent redirection lease across clock inspection and stream activation is a candidate architecture change to investigate after those markers locate the failure; extending timeouts or repeatedly retrying startup would not resolve ownership uncertainty by itself.

## Persisted startup journal and inspection-only mode

The diagnostic probe now supplies a separate `worker-N.tsv` path to each fresh native worker. The optional native `--startup-log` argument is valid only with `--stream-worker`; other modes reject it before file creation. Production ASIO configuration leaves this diagnostic path empty. With no configured path the journal performs no file I/O.

Each startup journal is created with `CREATE_NEW` on a local fixed drive and write-through enabled, so an existing file cannot be overwritten. A single control-thread writer records uptime milliseconds, worker PID and a fixed marker. Markers bracket helper loading/unloading, enumeration, configuration reads, redirect start, system-handle acquisition, clock getter and redirect close. Records preserve Win32 last-error state. No PCM, USB payload, descriptor strings or authentication material is recorded, and the audio request/callback path writes no journal records. Journal write failure contains the isolated worker rather than silently claiming complete diagnostics.

An unmatched entry marker identifies the last durably observed boundary; it does not by itself prove the instruction pointer is still inside that call. API exceptions, containment or an interrupted later marker write must be reconciled with the probe/process/trace records. Startup file writes can perturb timing, so a successful instrumented reopen alone would not establish an uninstrumented timing fix.

`sl3_host_probe --inspect-reopen` uses the same hash-pinned host/worker inspection path twice, with a fresh worker for each inspection. It prepares no SDK audio banks, never issues typed stream start and reports zero requested stream time. Its success contract requires both inspections and normal ownership retirement, with zero callbacks/input frames/output submissions. There is no audio fallback after a failed inspection.

The traced wrapper accepts `-InspectOnly` for this mode. It still requires explicit `-Run`, elevation, Secure Boot, a reviewed running driver, current source/binary fingerprints, one exact SL3 and a complete bounded USB trace. It rejects a remaining native test process before device access. Audio prerequisites are not applicable to the getter-only mode, so prior capture/duplex arguments are rejected there; the actual bridge mode retains its same-worker capture/duplex requirements. Both modes record journal hashes and their last markers on failure as well as success.

The new checkpoint passes **33/33 Release, 33/33 Debug, 23/23 SDK-free and 48/48 Python**. Journal tests read a flushed entry while the writer remains open, verify error preservation and no overwrite, and reject relative paths. The simulated lifecycle also exercises two inspection-only sessions with no audio; the truthful simulated fixture still reaches and fails the native kind handshake, rather than merely rejecting the new CLI argument. A manual negative plan check confirmed journal arguments cannot create files in native plan mode. New binaries are archived under `artifacts/build/checkpoints/startup-journal-20261030/`; these software checks do not establish a physical reopen result.

The attempted `inspect-reopen-staged-20261030-01` administrator launch was canceled by Windows before the script started. Its result directory was not created and no native test process remained. There is no physical journal/inspection-only outcome from this launch; the last actual hardware outcome remains the second bridge failure above.

The owner explicitly requested the prompt again and accepted the fresh launch using the previously unused result path. The **first** worker's journal records completed helper load, enumeration and full configuration read, followed by `redirect_start.enter` with no corresponding return. No clock inspection completed and the second worker was never launched. The probe prepared no audio banks and recorded zero callbacks, input frames and output submissions. [Staged failure evidence](evidence/inspect-reopen-staged-20261030.json).

This locates the last observed boundary at `UsbDk_StartRedirect`, before the clock getter. It is not merely another failure to find the device in enumeration. It also establishes that, in the state following the preceding failed bridge run, a first redirect can stall: rapid second-open timing is not a complete description of the current fault. The marker is not a kernel stack trace and does not distinguish the helper's internal reset, attachment wait or handle-creation substeps.

The native probe ran from 17:09:39.338 to 17:09:59.430 UTC and again failed its bounded retirement contract after requesting containment. Worker PID 3948 remained visible at 17:10:33; by 17:11:42 no native probe or worker remained. These observations are consistent with, but do not prove entry into, the reviewed driver's 120-second attachment/detachment waits. The USB trace contains 17,207 events and zero event/buffer loss. Secure Boot remained enabled and the selected original device/security baseline matched afterward; those results do not turn worker containment into normal cleanup.

The wrapper's initial journal hash failed while the stalled worker still held the journal open. The journal itself remained readable and preserved all eight complete records. The corrected reader uses an explicit read/write-sharing handle, reads at most 64 KiB once, and hashes that exact observed prefix. It reports complete-record count, the last complete marker and a partial suffix flag; it does not claim a mutable live file is final. The original failed wrapper report is preserved unchanged. Three new Python regressions cover a live writer and later append, empty/truncated records, malformed data and the size bound; the complete Python suite passes **51/51**. No native binary changed for this reporting fix.

The owner was asked to remove all SL3 power for ten seconds and reconnect it before any further device test. That physical recovery step is still awaiting confirmation at this checkpoint. Do not retry `StartRedirect` merely because enumeration/configuration read succeeds or the prior process has disappeared. After confirmed recovery, the staged control-only test can distinguish a clean first open from the immediate second open; a retained device lease remains an architecture candidate, not an established fix.

The subsequent [post-power-cycle result and single-open implementation](single-open-host.md) supersede that pending step: a clean first inspection succeeded, the immediate second redirect stalled, and a later reconnect reported a descriptor failure. The new single-open streaming probe is software-tested but awaits restored enumeration and fresh physical prerequisites.
