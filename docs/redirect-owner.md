# Excluding overlapping SL3 redirect owners

Every rebuilt native `Device::open` now acquires an existence guard before calling UsbDk StartRedirect. A second cooperating worker fails immediately with `ERROR_BUSY` if the guard already exists. Same-thread recursion cannot acquire it again. Access denial or a name collision with another kernel-object type also refuses the open. There is no owner wait, polling, automatic retry or handoff.

This addresses concurrent attempts from independently created driver objects or diagnostics. It does not address sequential opening after a released redirect, and it does not keep a device alive across final COM Release. The existing within-object retained connection continues to survive successful audio Stop/Start and buffer recreation. Its final close releases the guard only after the existing alternate-restoration/helper-close path reports success. A failed explicit close does not release the guard; subsequent destruction or process containment can close remaining handles.

## Windows mechanism and scope

The fixed name is `Global\SL3Rebuild.Redirect.1cc5.0001.SL3.01.00.v1`. Production cannot override it through a command-line argument. Unique fixture names are available only to the C++ test boundary. The native selector still requires exactly one genuine descriptor-matching SL3; no hardware identity is substituted.

The guard uses the existence of a non-inherited, nonsignalled event. [CreateEventExW](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createeventexw) atomically reports whether the named object already existed, including a distinct error for a different object type. The worker never signals, resets or waits on the event. A protected DACL grants System full access and authenticated users only `SYNCHRONIZE`. Each guard requests only that right. This object carries no commands or data and grants no USB/driver permission. A precreated inaccessible object causes refusal.

The [global namespace](https://learn.microsoft.com/en-us/windows/win32/termserv/kernel-object-namespaces) gives cooperating sessions one name; Microsoft's extra creation privilege requirement there concerns file mappings and symbolic links. [Event access rights](https://learn.microsoft.com/en-us/windows/win32/sync/synchronization-object-security-and-access-rights) distinguish `SYNCHRONIZE` from event modification. No service, scheduled task, administrator launch or security-policy change is introduced. Global naming is implementation scope; other-user/session and mixed-integrity interoperability have not been physically exercised.

The guard only coordinates software that uses it. Older workers, vendor applications and other USB clients are outside it. Windows closes event handles when their owners exit; that is not a quarantine mechanism for a stalled USB stack. Neither event disappearance nor accepted helper close proves USB detachment, successful re-enumeration or safe reopening. The [known second-redirect stall](usbdk-detachment.md) and [pending phase comparison](hub-port-observer.md) remain acceptance gates. No USB recovery rule or timeout delay is derived from this guard.

## Actual validation

The Release build passed **48/48 native tests**. The new test runs real private processes and Windows objects without opening a USB device or loading a UsbDk helper. It checks same-thread and separate-process exclusion, no reuse of one closed owner, destructor cleanup, wrong-type collision, access denial without fallback, refusal of an empty fixture name, denied event-signalling rights, and guard disappearance after a private holder is terminated and its job retires. Reacquisition in that last fixture proves only Windows object cleanup; the fixture contains no USB work.

The actual read-only preflight passes current source/dependency hashes and the reviewed kernel signature. It does not freshly establish Secure Boot because the normal token cannot perform that privileged query. The earlier physical controls pass was independently regenerated against its archived worker and source; it does not validate this new worker. [Compact software evidence](evidence/redirect-owner-20261101.json) is regenerated by `scripts/export-redirect-owner-evidence.py`.

The previous unstarted collector plan was actually refused for a changed runtime before any process launch, then permanently disarmed with an abort marker. Fresh plans are required for the next attended capture. No UAC prompt, trace, binding/trust change, SL3 redirect, PCM or firmware operation ran during this implementation. Raw source/build/test files are preserved in `artifacts/build/checkpoints/redirect-owner-20261101`.
