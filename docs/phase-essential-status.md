## What Serato 2.5.5 did differently

Original-byte inspection of the pinned Windows 2.5.5.83 executable provides a comparison using the same SL3 identity. This was a static comparison. The historical application and Rane kernel driver were not launched or installed.

| Boundary | 2.5.5.83 SL3 path |
| --- | --- |
| USB arrival and descriptor | The RTTI-bound `CUSBAudioManager` handler `1401478d0` dispatches message `0x105` to `140147ad0` via `140147ab6`. The callback obtains a descriptor by USB identity at `140147b6b`. |
| Legacy driver handshake | Kind 5 takes the DriverAPI factory at `140147b99` and calls its `+0x70` slot at `140147ba6`. The SL3 slot resolves to `140691980`. It requires successful `sl3_open` state and calls the historical `sl3_driver_timer` export before comparing the returned value. A false handshake takes the failure branch at `140147be8`. [Legacy SL3 driver API](serato-generic-driver-fallback.md) |
| Primary selection | A successful handshake proceeds to another readiness check at `140147c86`. If that succeeds, `140147d22` passes the same descriptor to `140356a00`. The setter searches the registered descriptor table by pointer and stores the matching pointer at `140356a81`. The callback then queues event `0xfe` with that descriptor and its USB manager. |

The observed 5.0 paths stop at different points. In the USB-only test, the arrival was published but the USB audio manager never initialized to receive it. In the MIDI-paired test, Serato registered the composite without publishing a new primary-selection event. The historical timer handshake is a concrete part of 2.5.5's path. The named loader and DriverAPI kind are absent from the checked 5.0 executable paths, so the old handshake cannot be assumed to be a callable entry point in 5.0.
