# USB arrival registration during Serato startup

Serato 5.0.0.1278 queues ordinary USB arrivals and resolves listeners when it processes each queued message. The USB audio manager can receive an arrival published before its subscription if the arrival was queued and the listener is registered when the drain takes its listener snapshot. The ordinary registration adds the listener without the separate lookup that marks existing startup-state records. [Original-byte evidence](evidence/serato500-usb-subscription-20261107.json).

The USB audio manager and the DeviceManager USB-only publisher use the same checked `MessageSystem` global. The arrival publisher constructs message `0x2d4` on route 7 and publishes through slot `+0x58`. The manager registers for that message on route 7 through slot `+0x10`. The checked registration path searches a vector for the listener and appends a 16-byte record when needed, including when the vector grows.

For `0x692`, the manager instead uses slot `+0x20`. That path registers in a separate keyed collection, then calls a helper that matches existing records by message, address, route and subtype. The helper marks the matching records at offset `+0x30`. The ordinary arrival registration has no corresponding call in the checked path. The static analysis leaves pending deliveries, new publications and other replay paths open.

The publish path checks the message and calls a policy callback before the enqueue at `141545ae0`. It can enqueue the original, replace it or return without queuing it. The enqueue stores the message and a flag in the queue at `MessageSystem+0x158`. The drain at `141546370` swaps the queue into a local batch, then looks up and copies the listener vector for each message. Both registration and dispatch index the same collection at `+0x28` using message, address and route. The USB arrival uses `(0x2d4, 0, 7)`. The drain calls listener slot `+0x08`; for the USB audio manager that slot forwards to `+0x18`, the existing handler at `1407108e0`.

The earlier live trace saw the SL3 arrival being constructed and audio staying offline. It did not observe manager startup, subscription or handler entry. If a normal launch still stays offline, the next trace can distinguish the original arrival reaching the queue, the matching listener being present when the drain copies the vector, and entry into the USB manager handler. Construction alone leaves the publish decision unresolved. The order of construction and subscription alone leaves delivery unresolved. A handler hit followed by no ASIO load moves the investigation to descriptor lookup and primary-device selection.
